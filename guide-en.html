User Guide

Set up a project from nothing, edit S1000D data modules visually, validate them against XSD and BREX, and produce a PDF from one module or from a whole publication. The tool runs in two shapes: the desktop application on your own machine, and the web edition where several authors share one CSDB. The editor is the same in both.

⟨web edition⟩

Web edition — working together

The same editor, on a server in your own network. Nothing is installed on the authors' machines; a browser is enough. The data modules live in one place, it is visible who is editing what, and the state before every save is kept.

The desktop edition assumes a single user: the files are mine, the open module is mine. That assumption does not hold in a shared CSDB, so the web edition adds four things — accounts, project membership, a check-out lock and version history plus an audit log. The editor itself (editing, validation, PDF) is identical.

Installing the server (administrator)

The server is installed on exactly ONE machine. Nothing is installed on the others — they open http://<server-name>:8443/ in a browser and are already clients. There is no separate “client edition”, and none is needed.

Install it on two machines and you get two separate CSDBs: each with its own projects, its own accounts and its own locks, unaware of each other. That is a configuration error — everything about working together (the lock, the version history, who edited what) works because it is gathered on one server.

If you genuinely have two networks that cannot reach each other, that is not a “client” problem but a data exchange problem: take a ZIP from one side and bring it in on the other with Import. But then, if the same module is edited on both sides, the lock cannot protect you and the two versions diverge; decide in advance which side owns which modules.

Windows installer — the usual route. S1000D Web Edition Setup 0.45.4.exe is installed on the server; Node does not need to be present, the package carries its own runtime. Setup asks for the port and the data directory, then:

  • creates a task that starts the server under the SYSTEM account when Windows boots
  • adds a Windows Firewall rule for the chosen port
  • puts shortcuts in the Start menu: S1000D Editor (in the browser), Start / Stop / Restart the server, Settings, Log, Firewall rule, User guide
  • starts the server straight away
First sign-in: user name and password are both admin. Sign in, change the password when asked, then create the authors' accounts from the Administration screen.

If the server stops unexpectedly, a supervisor script restarts it after five seconds. After changing settings choose Restart the server; if you changed the port, run the Firewall rule shortcut as well.

On the first run an account is created whose user name and password are both admin. The sign-in screen says so while that is still true. Until its password is changed the account can do nothing at all beyond seeing itself, changing its password and signing out — the project list does not even open. That restriction is enforced on the server, not merely on screen: any client that can reach the port and calls the endpoints directly gets the same 403. Once the password is changed the account has full administrator rights. If S1000D_ADMIN_PASSWORD is set, the first account is created with it directly and no change is demanded — the route to prefer for unattended rollout. Later accounts are created from the Administration screen.

Lost the administrator password? Add set "S1000D_RESET_ADMIN=1" to settings.bat (the line is already there, commented out) and restart the server. The password returns to admin and must be changed at the next sign-in. Put the rem  back afterwards, or it resets at every boot. Projects, modules, version history and the other accounts are untouched.
From 0.31.0 the installer does this for you. If Sertifika uret (generate a certificate) was selected during setup, the server already speaks https on its first start and the TLS_PFX lines in settings.bat are filled in; the steps below are only needed to supply your own certificate, or to generate one later. To generate one later: Start menu → TLS Sertifikasi. A generated certificate is self-signed — the encryption works, but browsers warn until its root is distributed to the authors' machines; the command to export that root is printed while the certificate is created.
Do not use it without TLS. With no certificate the server listens on plain HTTP and warns at startup — passwords and documents cross the network in the clear. Setting it up is immediately below.

Installing a TLS certificate

The certificate can be given in either of two forms, both in settings.bat:

FormSettingsWhen
PFX / PKCS#12 TLS_PFX, TLS_PFX_PASSWORD What Windows gives you — no conversion needed
PEM pair TLS_KEY, TLS_CERT If you already have separate key and certificate files

An internal certificate authority (recommended). If your organisation runs AD Certificate Services or another internal PKI, use it. Its one real advantage: the root certificate is already in the trust store of every machine in the domain, so authors see no warning at all in the browser.

  1. Request a certificate for the server's name using the “Web Server” template
  2. Have every name an author might type put in the SAN (Subject Alternative Name) field — short name, FQDN, and the IP address if it is used. CN alone is not enough; modern browsers ignore CN and treat the certificate as invalid
  3. Export it with its private key as a .pfx and point TLS_PFX at it

Self-signed (closed network, or a quick start):

openssl req -x509 -newkey rsa:2048 -nodes -days 825 \
  -keyout server.key -out server.crt \
  -subj "/CN=s1000d.company.local" \
  -addext "subjectAltName=DNS:s1000d.company.local,DNS:SERVERNAME,IP:192.168.1.50"

The browser will still warn. To remove the warning, distribute server.crt into the clients' Trusted Root Certification Authorities store (done in bulk with Group Policy in a domain).

Export the PFX with AES. The Windows export wizard still offers the old TripleDES-SHA1 option, and some tools write RC2. The server's Node runtime cannot open those old ciphers and reports Unsupported PKCS12 PFX data. Choose AES256-SHA256 in the wizard; with openssl: 
openssl pkcs12 -export -inkey server.key -in server.crt -out server.pfx \
  -keypbe AES-256-CBC -certpbe AES-256-CBC -macalg sha256

If there are intermediate certificates: with PEM, paste the server certificate first into TLS_CERT and the intermediates below it, one after another. A PFX already carries the chain.

Then: save settings.bat and choose Restart the server. The log should now show an https://… address and the “no TLS” warning should be gone. With TLS on, the session cookie is marked Secure and an HSTS header is sent.

If the certificate path is wrong or the file cannot be opened, the server does not quietly fall back to HTTP — it writes the reason to the log and stops. If you asked for TLS, it will not run without it.
The data directory. Each project is a plain folder under data/projects/<id>/: data modules, ICN graphics, s1000d-style.json, s1000d-profile.json, s1000d-tm.json — exactly the same shape as a desktop project folder. You can copy the folder and open it on the desktop, or copy a CSDB prepared on the desktop into here. The multi-user bookkeeping sits beside it: .versions/ (the content before each write), .state.json (review status), and at the root users.json, projects.json and audit.log. Backing up = copying the data/ folder.

The server makes no outbound requests: schema validation and BREX are read from the local package.

If the other machines cannot connect: Start menu › Erisim Denetimi (access check). It tests every condition that has to hold for a machine on the network to reach the server — is it running, is it listening on all interfaces, what profile is the network in, is there an allow rule, and is there a block rule overriding it — and names the one that fails, with its fix. It runs once by itself at the end of the install.
Network profile. Setup adds a firewall rule only for the Domain and Private profiles — deliberately: opening the Public profile would expose the server on whatever network a laptop later joins (a café, a hotel). Windows usually marks a new non-domain network as Public, and if the server machine is on such a network the other computers cannot connect. Change the network type to Private in Control Panel › Network and Sharing Center, or run Set-NetConnectionProfile -NetworkCategory Private in PowerShell as administrator.

Deleting a project

The ✕ at the top right of a card on the Projects page — only a project administrator sees it.

Because deleting is not a one-click way to destroy a CSDB, there are three steps: how many modules and files would be lost is stated first, the button stays shut until the project name is typed by hand, and the default behaviour is reversible:

OptionWhat happens
Default The folder is moved on the server to data/.deleted/<project>-<timestamp>/. The project leaves the list; if it was deleted by mistake an administrator can put the folder back under data/projects/ and recreate the project
Delete the files permanently The folder really is deleted and no copy remains. Choose this when controlled documents must not stay on the server

In both cases the project memberships and any open locks in it are released, and the action is written to the audit trail (project.delete / project.purge) with the name of whoever did it.

The .deleted folder is never cleaned up on its own. Review it regularly, for disk space and for your document retention rules.

Importing a data set you already have

A new project starts empty. To bring in a CSDB prepared elsewhere — produced in the desktop edition, coming from another tool, or restored from a backup — use the Import… button on the project board. There are two routes, and they end in the same place:

RouteWhen
Choose files… When you have individual files — several modules and graphics can be selected at once
Choose a ZIP archive… For a whole folder. Zip it and hand it over; sub-folders are flattened and the __MACOSX and .DS_Store leftovers macOS adds are discarded

The file types accepted: data modules (.xml), ICN graphics (png, jpg, gif, svg, cgm, and audio/video) and project settings files (s1000d-style.json, s1000d-profile.json, s1000d-tm.json). Anything else is listed as “unsupported” and skipped.

The plan is shown before anything is written. The table names each file (for a module: its DMC, title and schema), its size, and what will happen to it:

StatusMeaning
Will be addedNot in the project; it will be written
Identical, will be skipped A file of that name is in the project and its content is the same — writing it would change nothing, so it is skipped even with the overwrite box on. Most modules in a migration are like this; these rows need no decision
Differs — will be skipped A file of that name is there but its content is different; the box is off, so it is left alone. The size and modification date of the file in the project are printed under the row, so you can see which side is the newer work
Differs — will be overwritten The box is on; the previous state enters version history and you can return to it from History
Open by someone else, will be skipped Another author is editing that module — the lock holder is named
Same name twice, will be skippedYour selection contains two files with one name
XML could not be read, will be skippedThe file is not valid XML

If an ICN referenced by a module is neither in the selection nor in the project, it is listed as a warning at the top — so you notice you forgot the graphics before you meet an empty box in the preview.

The comparison is of content, not of dates. XML files are compared with line-ending differences normalised away, so a data set does not read as “changed” merely because it passed through a Windows machine. The rows that really need a decision are then not lost among the ones that do not.
The lock applies to import as well: a module someone else holds open cannot be overwritten. A bulk operation is not a way around a rule that holds for a single save.

User administration

Administration in the top bar (global administrators only) is the one place for accounts: the roster on the left, the selected person in full on the right — their details, role, which projects they are in, their open sessions and their recent actions.

Creating accounts. One at a time with New user, or from a list with Add in bulk. In bulk, each line is one person — user name, display name, role, unit, e-mail — and the lines are shown as a table before anything is written; a bad line fails on its own and the rest are created.

Passwords. Leave the password field empty and the server generates one. A generated password is shown exactly once, in the dialog that follows; what is stored cannot be read back. Pass it on securely; the person is asked to change it at first sign-in. Reset password works the same way (type one, or Generate one).

People who leave. Three separate actions, in order of severity:

ActionWhat it does
End sessionsDrops open browser sessions and releases the locks held; the account remains
DisableBlocks sign-in and releases sessions and locks; the account and its memberships remain
Delete userRemoves the account, its project memberships, sessions and locks

Deleting does not touch what the person wrote: modules, version history entries and audit.log lines keep the user name — “who changed this module” must still be answerable after someone has left.

You cannot take the administrator role from yourself, disable yourself or delete yourself; that is what keeps an installation from ending up with no administrator.

Projects. You can add and remove the person from projects here and change their project role — the same work as the Members tab on the project board, seen from the person's side. Download CSV gives the whole roster (role, unit, last sign-in) as a table.

The lock (check-out)

Opening a module takes its lock automatically and the top bar reads ✓ yours. While you are there, that module is read-only to everyone else.

  • If the lock is not yours the badge reads read-only, a notice says “A. Novak is editing this module” and the editor does not allow editing at all. That is deliberate: there is no point inviting work that will be refused at save time.
  • Moving to another module releases the previous lock and takes the new one.
  • A lock expires after 30 minutes; it renews itself while your tab is open and is released when you close it. An author who shuts the machine down does not leave anyone locked out.
  • A project administrator can take a lock over with release on the board; that action is written to the log with who took it from whom.
  • The other modules read during validation, publication assembly and translation (BREX, the sibling language, the modules entering a publication) take no lock — the lock is only on the document you opened.
Why is there no simultaneous co-editing? The editor's correctness rests on a lossless XML round trip: the DOCTYPE is preserved and inline structures (cross-references, acronyms, applicability) are written back verbatim from their original XML. Merging two people's character-level edits at the XML level would quietly corrupt the module you are about to deliver on every bad merge. CSDB practice expects this anyway: one author works on a module, the others see it live but read-only.

Version history

The state of the file before every save is kept. The module's History link on the board lists the versions with who wrote them and when; View shows the content and Restore takes you back. Restoring is itself a save: the current content joins the history, and nothing is lost.

Setting a project up in the web edition takes two steps. The New project button on the Projects screen opens the project: you give it a name and add the members — but it is empty. The modules come in the second step: open the project, choose Open the editor and run the Home → New Project wizard. Because the project you are in is empty, the wizard writes the modules into it — no second project appears and the members stay put. Run the same wizard in a project that already has modules and it asks for a new project's name instead; existing modules are never overwritten.

Documenting a new system

If you are starting from nothing rather than opening an existing data set, this is the order to follow:

  1. Set the project up — ✨ New Project

    The wizard asks for the project identity and writes four files into the folder you choose.

    FieldWhat it is forExample
    MICModel Identification Code — the first part of every DMCELD01
    Product nameUsed on the cover and in titlesRadar System
    Company codeCAGE/NCAGE — 5 charactersTR123
    Language / countryThe file name and the language elementen / US
    VersionsApplicability variantsMk1, Mk2

    The files created: an ACT (applicability cross-reference table), a BREX (the project's business rules), the first descriptive module (opened automatically) and the publication module.

    The wizard never overwrites existing files; if a name is taken it skips that file and says so in the status bar.

  2. Decide the SNS

    Before you start producing modules, settle the product's breakdown into systems — systemCode and the codes below it come from there. The Example SNS folder in the S1000D package has ready-made templates.

  3. Produce the modules — ＋ New Module

    The project details (MIC, company, language) are inherited from the open file. Choose a type — descriptive, procedural, parts catalogue or front matter; the info code is set to match (040 / 520 / 941 / 001). Enter the technical name and the info name and adjust the DMC fields; the DMC and the file name are previewed live.

    The technical name and info name are pre-filled by type so you can create a module straight away; both can be changed. Empty a required field and the create button is disabled, with the missing field named beside it.

    The skeleton produced is complete for its type (preliminary requirement blocks in a procedure, a first part row in an IPD) and its brexDmRef and ACT reference are wired up.

  4. Narrow the BREX to your project — ⚖ BREX rules

    • Rules are listed with NOT ALLOWED / REQUIRED / VALUE badges
    • + Ready-made rule adds the XPaths in common use as complete rules (system code, security classification, manufacturer code…); + Empty rule is for a path of your own
    • Permitted values may be single (ELD01), a range (DA0~DA9) or a pattern (regex)
    • On save the rules are written into the BREX module and appear on the page at once: a table of object path, status, description and permitted values — you can read your own rule book and hand it out as a PDF
    • From then on ✓ Validate checks every module against these rules

  5. Enter the IPD data

    ＋ Part row adds one part (item, indent, part number, manufacturer, description, quantity, SMR); below the selected row if there is one.

    ⇪ Import BOM takes the parts list from engineering as CSV: the delimiter (, ; TAB) is detected, quoted fields are supported, and the columns are matched from the header names (English and Turkish). Check the preview, then import with either append or replace the existing list. Rows with no item number are numbered 010, 020, 030… automatically. This window opens by itself when you create a parts catalogue module.

    Service code: for rows that carry an SMR code, the S1000D schema also requires a service element. The import window asks for it once and applies it to every SMR row; without it the import is blocked, because otherwise it would produce a module that fails validation.

  6. Define the platforms — 🎯 Applicability table

    This is the answer to one piece of content being used on several platforms: a radar may sit on a frigate, a corvette and a fast attack craft. The S1000D way is not to copy the content but to keep one source and mark where each piece belongs — the Common Source in CSDB says exactly that.

    Open the project's ACT module (00W); the 🎯 Applicability table button on the BREX tab opens the editor. Each property is an identity and a set of values:

    IdentityDisplay nameValues
    platformInstallation platformFRIGATE, CORVETTE, FASTATTACK
    versionVersionMk1, Mk2
    hullHull number(empty — free text)
    An identity cannot be changed later. The applic expressions in modules refer to it, and renaming it would break those references. If you remove a property, the expressions in the modules stay as they are — they count as “undecided” when filtering.

    You state that a module belongs only to certain platforms in that module's applic section (Document Map › right-click › Change…, or XML mode). An unmarked module belongs to every platform.

    Publish — and filter by platform

    Add the module references under pmEntry in the PMC file — then 📄 PDF produces the cover, the contents and every module in one file.

    One publication module, a book per platform. With a publication open and properties defined in the project's ACT, a bar appears at the bottom of the window:

    Compile this publication for: Installation platform [CORVETTE ▾]Hull number [____] Clear the filter

    Choose a value and the publication is recompiled at once: modules that do not belong to that platform stay out of the book, and platform-specific blocks inside a module are removed too. The status bar counts how many modules fell out of scope and how many blocks were filtered. With nothing chosen the publication compiles in full, as before.

    The cover of a filtered publication is stamped with the platform it was printed for. Two books produced from the same PMC differ only in that line; once printed, nothing else tells them apart.

    Take the “applic could not be evaluated” warning seriously. If the tool cannot resolve an expression with certainty it leaves the content in rather than removing it, and counts that. Silently dropping a warning or a torque value because of an expression it did not understand is far more dangerous than leaving extra content in. There are two usual causes: a property you did not choose, or a condition expression tied to a service bulletin state — which the tool cannot know. Review those modules before the book goes out.

    The files never change: filtering applies only to the compiled publication, and the modules on disk stay as they are.

Visual (WYSIWYG) editing

The application opens in Visual mode: you see the document laid out as printed pages and work directly on it. Every change is written back to the XML in the background within half a second — DOCTYPE and entity declarations included, the source file is preserved without loss.

Editing text

  • Paragraph, title, table cell, figure caption, warning text… click and type.

Adding a figure

🖼 Figure attaches an image to the module. In S1000D a figure is not linked by file path but through a graphic declaration (ENTITY) in the DOCTYPE — the application does that for you:

  1. Choose the file (PNG, JPG, GIF, SVG, CGM — CGM is decoded in the preview too)
  2. Confirm the suggested ICN identifier and the figure title. The identifier is derived from your company code; if the file name already starts with ICN- it is kept, because other modules may refer to it
  3. On Add, the file is copied into the module folder under that name, NOTATION and ENTITY declarations are added to the DOCTYPE (which is created if absent), and the <figure> is inserted below the selected block

Text formatting

The B / I / U / X₂ / X² buttons on the toolbar (or ⌘B ⌘I ⌘U) turn the selection into S1000D's semantic elements: emphasis, emphasis em02, emphasis em03, subScript, superScript.

Why is there no font or type size? S1000D is a semantic markup language: the content says “this is emphasised”, not “this is 12pt Arial”. There is no font attribute in the schema. Typography is decided by the style definition at publication time — so the same data module can print consistently in different publications and under different customers' house styles. If you want to change the appearance, the right place is the publication style, not the inside of the document.

Untouchable items (atoms)

Cross-references (Fig 1 Para 1.2 Step 2.1), DM references, acronyms, index flags (⚑) and hotspot references behave as one piece: their insides cannot be broken, deleting one removes it whole, and they return to the XML verbatim.

⟨s-series⟩

The S-Series bridge — 🔗

Within the ASD/AIA S-Series family, S1000D covers only publication; parts provisioning (S2000M), preventive maintenance analysis (S4000P) and logistics support analysis (S3000L) are separate specifications. These four commands carry that other specifications' data directly into S1000D data modules — without retyping it.

All four are context-dependent: they stay greyed out until the right kind of module is open. What each one needs is listed below — faster than hunting for it in the ribbon.

S2000M → IPD

With an IPD module open: Home → ⇪ Import BOM. The file's content is inspected, not its extension: if it is an S2000M provisioning message (locipd), column mapping is skipped entirely — part number, manufacturer code, description, the quantity per next-higher assembly and the NSN are read directly. The same command also accepts a plain CSV, in which case the column-mapping step appears.

S2000M keeps the NSN split across two fields (supply class + item identification number); S1000D splits it into three. The conversion is automatic, and the manual-entry form carries the same NSN column.

S4000P → Scheduled maintenance

This one needs a scheduled-maintenance (schedul) module first — create an empty one with ＋ New Module → Maintenance plan / time limits. With that module open, Home → ⏱ Import S4000P appears: the threshold value, its unit and the limit's description are read directly from the S4000P analysis file you pick (pmaDataset).

S1000D's thresholdUnitOfMeasure list is a closed set of codes; S4000P uses its own vocabulary, so a unit conversion happens and is shown in the preview. A row marked "≈" means both definitions describe the same thing but S1000D's equivalent is narrower or wider — review it before importing. Units with no S1000D equivalent can be assigned a project code (th51-th99) in the mapping profile; left unassigned, that threshold is skipped, and the import states how many before you commit.

S3000L → Procedure skeleton

With project parameters defined (a project open): Module → ⚙ Module from S3000L. Unlike the other three, this one does not edit the open document — it writes new files: one empty-bodied procedural (proced) module per usable task in the LSA data set (lsaDataset) you pick. A task's information code (taskInformationCode) maps directly to the S1000D information code; if the LSA declares a target data module (resDM) its DMC is used, and if it does not, the DMC comes from the defaults in the mapping profile — the preview shows, row by row, which source each one came from.

Step text is never generated. LSA states how long a task takes, not how it is performed; the body arrives with a "Write the steps here" placeholder for the author to fill in. If two tasks land on the same DMC (different parts, the same information code, say), the second is not produced — rather than overwrite the first, the conflicting tasks are reported.

Mapping profile

Module → 🔗 Mapping Profile (with any module open). Both decisions edited here belong to the project, not the specification: a project code for S4000P units with no S1000D equivalent, and DMC defaults (system, sub-system, assembly...) for when S3000L does not declare a target module. It is written to the project folder as s1000d-mapping.json and read automatically on every later import.

Only th51-th99 are accepted. th01-th39 are S1000D's own definitions (Table 81); mapping an S4000P unit there would assert a meaning nobody has verified. A unit that already has a standard equivalent cannot be overridden by the profile — the profile does not replace the specification, it only fills the gap the specification deliberately left.

The other direction: the S3000L catalogue

With a project folder open: Publication → ↗ S3000L Catalogue — no dialog, one click. It scans every data module in the folder (files prefixed DMC-...) and produces the document records the LSA's resDM declarations point to, writing them to S3000L-belge-katalogu.xml in the same folder. The four flows above all ran one way, from S-Series into S1000D; this one reports back what the publication side actually produced. The generated message validates against the real S3000L 3.0 schema.

All three import panels carry a collapsible diagnostic note (closed by default): it counts which containers in the file you picked are populated, how many were read, and why the rest were left out of scope. When fewer rows come out than you expected, this is the first place to look — it tells you whether to blame the file or the tool.

⟨s1000d-issue⟩

The S1000D issue — Issue 6 and Issue 7

A CSDB is at one issue: every module in it declares the same schema package, and its BREX and business rule decisions belong to that issue. S1000D asks this as a decision point of its own (BRDP-S1-00003). The issue is therefore a project setting, not a per-file one.

You choose the issue in the New Project wizard; the default is Issue 7. When you open an existing data set the application reads the issue from the files themselves, so your older Issue 6 projects keep working as they are, and new modules produced inside them declare Issue 6 too.

WhatHow it behaves

GenerationModules, the ACT, the BREX and the publication module declare the project's issue
Older samplesFiles declaring Issue 5.0 are met with the Issue 6 package rather than rejected
Issue 7 is a superset of Issue 6: 22 elements were added, none removed, and no value list this tool uses changed. An Issue 6 module therefore also passes the Issue 7 package — but that is not a reason to mix the two: writing an Issue 7 module into an Issue 6 CSDB leaves the data set declaring two issues at once.

Release history

What changed in each version, newest first. The version you installed is named in the colophon at the foot of this page.

  • 0.45.4 — A splash screen at start-up. The desktop application now opens with a splash screen showing the version, the author (Rahmi Gökhan VURAL) and the contact address (rgokhanvural@outlook.com). It stays for at least 5 seconds before the main window appears; if loading hangs it closes after 20 seconds at most.

The cause sits at both ends of the chain: XML parsing normalises CRLF to LF before the text ever reaches the DOM, and XMLSerializer emits LF. The prolog, which is sliced out as text, kept its CRLF — so the file ended up with mixed line endings and the module showed as every line changed in a diff. For an author working on Windows that made version history and review unreadable. The source's own convention (by majority) is now restored; LF files are unaffected, not a byte differs.
    • The new test suite found this. npm test now chains eleven checks alongside the typecheck and runs 306 assertions. New ones cover round-trip and format preservation, renderer security (XXE, entity expansion, deep nesting, oversized values), validator security and path traversal, the XSD validation contract, and schema-declaration reading.

The asymmetry came from the two patterns having been written separately.
